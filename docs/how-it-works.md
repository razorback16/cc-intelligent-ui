# How it works

← Back to the [README](../README.md)

## The steps

1. A `ui.render` hook on `AssistantMessage` gets each block of the answer as Markdown.
2. While Claude writes a block, Claude Code shows its own text: Claude Code gives the hook the text of a block only when the block is complete (versions 2.1.299 to 2.1.303 at least). The block is final when the model request starts its next block (a tool call, more text) or ends. If the mod did not see the request, the block is final after its text stops changing for 400 ms. Then the mod writes the block to a JSON file and runs `typst compile` with `render/md.typ`. For plain text, Typst loads only some fonts (refer to [The lean font set](#the-lean-font-set)). Long answers are cut at block boundaries into pages. One page is one PNG.
3. The hook draws one `Image` per PNG, in place of the text.
4. Text size: the mod finds the terminal font (iTerm2 profile, Ghostty, kitty or Rio config; on Linux, else fontconfig's `monospace` font; else the metrics of the theme's code font, Menlo on macOS) and the cell size in pixels. Typst then measures both fonts so that 100% looks as large as the terminal text. Body text and code use the terminal font, so at 100% they are exactly the terminal's size. Ghostty and cmux draw their own JetBrains Mono when their config names no font. This font is not a file: it is inside the Ghostty program. The first time, the mod copies it to `~/.cache/cc-intelligent-ui/fonts/` (approximately 0.1 s, once for each Ghostty version), so that Typst can draw it. In Ghostty and cmux, the mod also removes the window padding from the cell size, because Ghostty adds the padding to the pixel size that it reports.
5. If a compile fails (a bad Typst block or an unknown LaTeX command), the mod compiles once more in safe mode: Typst blocks and math show as code. A dim line under the picture names the error. If that also fails, the normal text shows.
6. Pictures are kept in `${TMPDIR}/cc-intelligent-ui-<uid>/` (`/tmp` when `TMPDIR` is not set). Folders older than 2 days are deleted at start. The drawing space of each answer at its first compile is kept in `~/.cache/cc-intelligent-ui/designs`, so that its Typst drawings keep the same share of the screen in later sessions.
7. Links: the mod finds the web links, file paths and commands in the Markdown (not in code blocks or math). It draws one dim row for each under the pages, with a `Link` (an OSC 8 link) for a web link or a file, and a `Button` that copies a command (`$.ui.copy`). It keeps a file row only when the file exists (`$.fs.exists`, kept in memory for 512 paths). Each row is one terminal row, cut at its end. The copy (step 9) counts these rows under the pages, so it still finds the page that you select.
8. The plan: a `ui.render` hook on the ExitPlanMode `ToolUse` row draws the plan through the same steps. Claude Code shows that row above the approval question. The approved result row then shows only its header, so the plan does not show two times. A `tool.call` hook on ExitPlanMode asks the mod's question (`$.ui.ask`) before Claude Code asks for permission. Then a `classic.PermissionRequest` hook gives the answer to Claude Code at once, so the Claude Code dialog does not show. For an approval, the hook sends the plan (`updatedInput`) and the new permission mode (`setMode`). For the person's text, the `tool.call` hook refuses the call with that text.
9. Copy: Claude Code writes a copy (copy on select in fullscreen mode, `/copy`, `$.ui.copy`) with a tool that it starts by name from the `PATH`, as its direct child: `pbcopy` on macOS, and `wl-copy`, `xclip` or `xsel` on Linux. Before it starts the tool, it also sends the text to the terminal (OSC 52). At the start, the mod writes a small `sh` script (a shim) for each of these tools that is installed, into `<cache>/shims-<pid>/`, a folder of this Claude Code process only. It also makes the folder `<cache>/ask/` (mode 700) and the FIFO `<cache>/ask-<pid>` (mode 600) for this process. It does this only when the cache folder, the shims folder and `ask/` are folders of your user, not links, and not writable by other users (`hooks/clip-shim-setup.sh` checks this). It never uses the shared fallback folder `/tmp/cc-intelligent-ui` for this. It does not do this over ssh, in a background session, or in a terminal that shows no pictures. It puts the shims folder first on the `PATH` of the Claude Code process, one time, and sets `IUI_COPY_ASK` to the FIFO (`$.env.set`). With no `perl`, it makes no shims. Each shim has the full path of `perl`. When the mod draws its first picture, it starts a reader: a small `perl` process that keeps the FIFO open and gives the mod each name that a shim writes to it. The reader stops when Claude Code stops. If the reader stops for a different reason, the mod starts it again after 1 s (3 times at most).

   A shim asks only for a clipboard write of text (with no type, or a text type: `text/plain…`, `UTF8_STRING`, `STRING` or `TEXT`), and only when its parent is the process of the FIFO (the number in `ask-<pid>`). Other calls (a read, the primary selection, an image type) go to the real tool with no change and with no `perl`. For a write, the shim starts `perl`, which keeps the text in memory. If the text has picture cells (the bytes of U+10EEEE) and is 4 MiB or less, `perl` writes it to a request file `ask/<pid>-<shim pid>-<time>` (mode 600) and writes the name of the file to the FIFO. Before that, it makes sure that the FIFO and `ask/` are of your user and are not links. If no reader has the FIFO open (for example, the mod stopped), the open fails immediately, and the shim uses the cells. `perl` waits for the answer file for 1.5 s at most from its start, because Claude Code stops the tool after 2 s. Then it gives the answer (or the cells, when the answer is empty or did not come) to the real tool through a pipe, with the same arguments, and gives the exit status of the tool (also a signal). The shim deletes the request and the answer. It writes no other file. The mod takes only names of letters, digits, `.`, `_` and `-` from the FIFO (never a path), and reads the request file only in `ask/`, at most 4 MiB. It finds the text under the cells (see below). When the mouse selection of its session is that copy, the mod uses the row of the selection. It always answers: with the text, or with an empty answer when it cannot read the cells, so the shim does not wait. It writes the answer (mode 600) to a temporary file, then makes a hard link with the answer name. If the shim stopped waiting, the shim made that name first, so the link fails. Then the mod writes nothing to the clipboard: a different session can copy the same cells at that time. It deletes the request and the mark, and a toast tells you to use `/iui grab`. The mod writes the clipboard only in its answer to its own shim, and in `/iui grab` and the `ui.copy` hook. At `/clear` or a resume, the reader continues. At other session ends (for example `/exit`), the mod stops the reader and deletes the FIFO, the request files and the shims folder of this process. At the start, the mod deletes the FIFOs, the request files and the shims folders of processes that stopped, and request files that are older than 2 days. It does nothing in a cache folder that is a link or that is not yours.

   One long-lived `perl` process (the watcher) watches the terminal size (at each SIGWINCH) and the clipboard. On macOS, it uses `/usr/bin/perl` with Apple's PerlObjCBridge and reads the change counter of the clipboard (`NSPasteboard changeCount`) every 0.3 s. This read is in the process and starts no other process (approximately 0.05% of one CPU core). On Linux, the process starts a child in a process group of its own. The child runs a tool that prints a line at each clipboard change (`wl-paste --watch`, `clipnotify` or GTK 3 from Python, refer to [Linux](install.md#linux)) and gives the mod a counter for each line. Nothing runs between two changes. When the `perl` process stops, it stops that process group. The clipboard part starts only while the mod is on and after the mod drew its first picture in this session; then the mod starts the process again with the clipboard part (and again without it after `/iui off`). When the counter changes, the mod reads the clipboard one time (`pbpaste` on macOS; `wl-paste`, `xclip`, `xsel` or GTK on Linux). The mod never changes a copy of picture cells that no shim of this session asked for (a copy of a different session, or of the terminal itself on the main screen). When these cells fit a page drawn in this session, it shows one toast that names `/iui grab`. In fullscreen mode, it first waits 2 s, because the OSC 52 copy can come before the shim asks. `/iui grab` then reads the picture cells on the clipboard and writes their text. The first counter after a start is not a change, so an old clipboard gets no toast. If the watcher stops, the mod starts it again after 1 s (3 times at most). At `/clear` or a resume, the watcher continues without the clipboard part. At other session ends, the mod stops it and does not start a new one.

   A picture cell holds its row and its column (kitty placeholder U+10EEEE plus two combining marks). The mod finds the drawn page that has these rows, at the size that it is drawn. Then it finds the position of each word on that page: it runs the probe (`typst query` on the same template, with the same inputs as the PNG compile, plus `probe=1` and `page=<n>`) for the selected pages only. The mod keeps the positions of the last 64 pages in memory. It writes nothing to disk for this, and the PNGs do not change. The mod takes the words in the selected cells. A `ui.copy` hook also changes a copy with picture cells to the text.

## Picture select

From Claude Code 2.1.305, the mod's `Image` has `noSelect`: the selection painter and the copy on select of Claude Code skip picture cells. Thus the mod selects pictures itself (`hooks/lib/select.ts`):

1. Each page is in a `Box` of its size. The last child is a `Client` (`hooks/sel.tsx`) in a `Box` with a negative top margin (the page's rows), so it is over the page. The `Client` draws only an empty `Box` (anything that it draws hides the picture cells). It takes the pointer and posts the selection whole: the anchor, the head, the phase (`down`, `move`, `up` or `clear`) and an order. Posts of one frame merge, so a bare event could be lost.
2. The `ui.message` hook keeps the newest selection. The selected rows are in stream order, in the rows of the whole drawing, so a drag can go on into the next page.
3. The highlight does not change the layout. Each page stays one keyed `Image`, and the mod swaps its picture with `$.ui.blit` (`hooks/lib/blit.ts`). This is one small kitty command with the same image id (`a=T`, `t=f`, the file name), so the terminal replaces the picture in place. The frame is the page with the selected cells changed: in a selected cell, each pixel of the page (straight alpha) over the opaque selection colour; in the other cells, the page as it is. A clear swaps the page's own PNG back. Cell `i` is the pixels from `round(i × pixels / cells)` to `round((i + 1) × pixels / cells)`, so the cells cover the page with no gap at any ratio.
4. The hooks runtime has no zlib, so `hooks/lib/png.ts` decodes the page in JavaScript (inflate and unfilter) at the first `down` on it, one time. The mod keeps the decoded pages in memory, 128 MB at most (about two pages of 3392 × 4284 pixels). For each row of cells, it makes a deflate piece one time (fixed Huffman codes, matches of one pixel to the left or one pixel up, ended on a byte). A row that is selected whole has a tinted piece, also made one time. A frame makes new pieces only for the first and last selected rows (partly selected), and joins the pieces into one PNG (about 1.5 MB for a page of 3392 × 4284 pixels). The hooks can write only text, so `perl` writes the frame (base64 on its stdin) to `<cache>/select-<id>/f-<n>.png`. The terminal reads the file after the blit. The mod deletes a frame file when 4 newer frames are written and it is 2 s old. The 2-day cleanup of the cache folder deletes the rest.
5. A new frame starts at most once in 16 ms, and only after the last one is blitted. The posts between fold into one frame of the newest selection. If Claude Code refuses a blit, the mod writes the reason one time to the debug log and shows no highlight on that page until the next `down`. The copy still works.
6. At `up`, the mod reads the words under the selected cells the same way as for a copy of these cells (`textOfRun` on the words of the probe), and copies them with `$.ui.copy`.

The `Client` is in the flow, not in an absolute `Box`. Claude Code (2.1.306) moves an absolute `Box` whose top is above the screen down to row 0, with its children. Then the pointer `y` of a `Client` in such a `Box` counts from row 0 of the screen, not from the top of the page, so the selection was too high by the rows that were scrolled away. Also, the `Client` took the pointer under the page. A `Box` in the flow has its true position, also when its top is above the screen.

A `Client` over a picture also takes the selection from Claude Code before 2.1.305 (which selects and copies pictures itself), so the mod draws it only from 2.1.305 (`$.session.version()`), in fullscreen mode. A `Client` that fails (`ui.fault`) turns picture select off until a reload.

## The lean font set

At each start, Typst reads all the fonts of the computer. On macOS, this is approximately 70 ms of each compile. Plain text does not need most of these fonts. Plain text has only ASCII characters, no math outside code, no live Typst block, no image and no HTML entity. In the answers that we measured, approximately 3 of 4 blocks are plain text.

For plain text, Typst loads only these fonts:

- The terminal font.
- The body fonts and the code fonts of the theme, but not the CJK fonts and the emoji fonts.
- The fonts in Typst (for example, the math font).

The mod puts links to these font files in one folder in the cache (`fonts-<hash>`). It gives Typst `--ignore-system-fonts --font-path <folder>`. Then a block of plain text compiles in approximately 0.03–0.07 s, not 0.1–0.15 s. The PNG does not change. For ASCII text, Typst takes each character from the first font of the list that has it, and that font is in the folder. Other text can need a character that no font of the list has. Then Typst looks in all the fonts of the computer, so other text compiles with all the fonts.

The mod makes the folder one time in each session, after the first compile of plain text. `typst fonts --variants` gives the files. The mod does not use the folder in these conditions:

- The first installed font of a list is a CJK font or an emoji font.
- A list has no installed font.
- One style of a font is in two files (then the order in which Typst reads the files can change the font that it uses).
- The list markers or the numbering of the theme are not ASCII.

If a compile with the folder fails, the mod compiles again with all the fonts. The probe of a copy (step 9) uses the same fonts as the PNG compile. If the folder is not there (the cleanup at start deletes folders that are older than 2 days), the mod uses all the fonts and makes the folder again.

## How `auto` is resolved

Claude Code finds the light or dark mode for `auto` by asking the terminal for its background colour (OSC 11). A mod cannot see that answer, so Intelligent UI uses these sources, in this order. The first source that gives an answer is used:

1. **The iTerm2 profile:** the background colour of the profile in use (`ITERM_PROFILE`, else the default profile). Intelligent UI finds iTerm2 by `TERM_PROGRAM`. If `TERM_PROGRAM` is not set, `ITERM_PROFILE`, `ITERM_SESSION_ID` or `LC_TERMINAL=iTerm2` also show iTerm2. If the profile has separate colours for light and dark mode, Intelligent UI uses the set for iTerm2's theme (Settings > Appearance). If that theme is Automatic, Minimal or Compact, it uses the set for the OS appearance.
2. **The Ghostty config:** the `background` that `ghostty +show-config` gives. With a `theme = light:A,dark:B`, Intelligent UI reads the background from the theme file for the OS appearance. With no theme and no `background`, it uses Ghostty's default (`#282c34`, dark).
   - **cmux** (Ghostty inside, found by its `CMUX_*` variables) reads the same Ghostty config, then its own config, `~/Library/Application Support/com.cmuxterm.app/config.ghostty`. The cmux themes picker (Settings > Themes, `cmux themes`) writes the theme there, and that theme wins over the Ghostty config's. A `light:A,dark:B` theme follows cmux's appearance (see below). If these configs set no `theme`, `background`, `foreground` or `palette`, cmux uses its adaptive default theme. Intelligent UI then uses cmux's appearance: `app.appearance` in `~/.config/cmux/cmux.json`, else the value in cmux's Settings. If that appearance is System, Intelligent UI uses the OS appearance. If `terminal.adaptiveDefaultTheme` is `false` in `cmux.json`, Intelligent UI uses the Ghostty rules above.
3. **The kitty config:** the `background` in `kitty.conf` and in the files that it includes (`include` lines only). The themes kitten writes such an include. If the config folder has `dark-theme.auto.conf`, `light-theme.auto.conf` or `no-preference-theme.auto.conf` (kitty 0.38 and later), Intelligent UI uses the file for the OS appearance, as kitty does (on Linux, the portal's or GNOME's colour scheme). With no `background`, it uses kitty's default (`#000000`, dark). The config folder is `KITTY_CONFIG_DIRECTORY`. If that is not set, it is the first of `$XDG_CONFIG_HOME/kitty`, `~/.config/kitty` and (on macOS) `~/Library/Preferences/kitty` that has a `kitty.conf`.
4. **The Rio config:** `config.toml` in `RIO_CONFIG_HOME`, else in `~/.config/rio` (on Linux, `$XDG_CONFIG_HOME/rio` if that is set). With an `[adaptive-theme]`, Intelligent UI reads the theme file for `force-theme`, else for the OS appearance. Else it reads the file for `theme`, else the `[colors] background`. Theme files are in the `themes` folder. With no background, it uses Rio's default (`#0F0D0E`, dark).
5. **`COLORFGBG`**, as it was when Claude Code started. Ghostty does not set it.
6. **The OS appearance:** macOS Dark or Light. On Linux, the `color-scheme` of the freedesktop portal (through `gdbus`, else `busctl`; "no preference" is light), else GNOME's `color-scheme` (`gsettings`). The mod keeps the tool that works, so each check starts one process.
7. **Dark.**

The terminal comes before the OS: a dark terminal on a light Mac is dark.

Intelligent UI checks every 3 s. After a change, each mode's pictures compile once. `/iui probe` asks the terminal for its background with OSC 11 (5 times) and shows the raw answers. This is a test of whether the answer can reach the mod. The 3 s check does not use OSC 11 yet.
