# How it works

← Back to the [README](../README.md)

## The steps

1. A `ui.render` hook on `AssistantMessage` gets each block of the answer as Markdown.
2. While Claude writes a block, Claude Code shows its own text: Claude Code gives the hook the text of a block only when the block is complete (versions 2.1.299 to 2.1.303 at least). The block is final when the model request starts its next block (a tool call, more text) or ends. If the mod did not see the request, the block is final after its text stops changing for 400 ms. Then the mod writes the block to a JSON file and runs `typst compile` with `render/md.typ`. For plain text, Typst loads only some fonts (refer to [The lean font set](#the-lean-font-set)). Long answers are cut at block boundaries into pages. One page is one PNG. The pages show one under the other with no space between them. Thus each page after the first starts with the space that its first block has under the last block of the page above it. The JSON file holds these two blocks for each cut, and Typst measures the space. On the row grid, this space is the same as in one page.
3. The hook draws one `Image` per PNG, in place of the text.
4. Text size: the mod finds the terminal font (iTerm2 profile, Ghostty, kitty or Rio config; on Linux, else fontconfig's `monospace` font; else the metrics of the theme's code font, Menlo on macOS) and the cell size in pixels. Typst then measures both fonts so that 100% looks as large as the terminal text. Body text and code use the terminal font, so at 100% they are exactly the terminal's size. The mod uses the font that the terminal draws: if the config names a font that is not installed, the terminal draws a different font, and the mod uses that font too (Ghostty and cmux on macOS, and Rio: their own font; Ghostty on Linux and kitty on Linux: the nearest font of fontconfig; kitty on macOS: Menlo; iTerm2: the user's fixed-pitch font, Menlo if you did not change it). If Ghostty's `font-family` is a list, the mod uses the first font of the list that is installed. Ghostty and cmux draw their own JetBrains Mono when their config names no font. Rio draws its own Cascadia Code NF when its config names no font (or `cascadiacode`). These fonts are not files: they are inside the program of the terminal. The first time, the mod copies the font to `~/.cache/cc-intelligent-ui/fonts/` (approximately 0.1 s for Ghostty and 0.5 s for Rio, once for each version of the terminal), so that Typst can draw it. If you set the `TYPST_FONT_PATHS` variable, Typst gets your folders and the copy. If the mod cannot copy Rio's font, it uses Cascadia Code if it is installed. If Typst does not have the terminal font, `/iui details` tells you, and the pictures use the theme's fonts. If the terminal font has no bold face (for example, Monaco), the pictures draw its bold text with a thin outline in the text colour (a fake bold, as a terminal draws it). The mod finds this with `typst fonts --variants` when it measures the fonts. In Ghostty and cmux, the mod also removes the window padding from the cell size, because Ghostty adds the padding to the pixel size that it reports.
5. If a compile fails (a bad Typst block or an unknown LaTeX command), the mod compiles once more in safe mode: Typst blocks and math show as code. A dim line under the picture names the error. If that also fails, the normal text shows.
6. Pictures are kept in `${TMPDIR}/cc-intelligent-ui-<uid>/` (`/tmp` when `TMPDIR` is not set). Folders older than 2 days are deleted at start. The drawing space of each answer at its first compile is kept in `~/.cache/cc-intelligent-ui/designs`, so that its Typst drawings keep the same share of the screen in later sessions.
7. Links: the mod finds the web links, file paths and commands in the Markdown (not in code blocks or math). It draws one dim row for each under the pages, with a `Link` (an OSC 8 link) for a web link or a file, and a `Button` that copies a command (`$.ui.copy`). It keeps a file row only when the file exists (`$.fs.exists`, kept in memory for 512 paths). Each row is one terminal row, cut at its end. The copy (step 9) counts these rows under the pages, so it still finds the page that you select. When the pages take picture select, the mod does not draw these rows (the links are live in the picture, refer to [Picture select](#picture-select)), and the copy, the plan and the Markdown files that Claude sent count 0 rows for them.
8. The plan: a `ui.render` hook on the ExitPlanMode `ToolUse` row draws the plan through the same steps. Claude Code shows that row above the approval question. The approved result row then shows only its header, so the plan does not show two times. A `tool.call` hook on ExitPlanMode asks the mod's question (`$.ui.ask`) before Claude Code asks for permission. Then a `classic.PermissionRequest` hook gives the answer to Claude Code at once, so the Claude Code dialog does not show. For an approval, the hook sends the plan (`updatedInput`) and the new permission mode (`setMode`). For the person's text, the `tool.call` hook refuses the call with that text.
9. Copy: in fullscreen mode, picture select copies the text of a picture (refer to [Picture select](#picture-select)). A copy that still puts picture cells on the clipboard is a native copy: the copy of the terminal itself on the main screen, a selection of Claude Code that starts outside a picture, or a copy of a different session. The mod never writes the clipboard for a native copy.

   One long-lived `perl` process (the watcher) watches the terminal size (at each SIGWINCH) and the clipboard. On macOS, it uses `/usr/bin/perl` with Apple's PerlObjCBridge and reads the change counter of the clipboard (`NSPasteboard changeCount`) every 0.3 s. This read is in the process and starts no other process (approximately 0.05% of one CPU core). On Linux, the process starts a child in a process group of its own. The child runs a tool that prints a line at each clipboard change (`wl-paste --watch`, `clipnotify` or GTK 3 from Python, refer to [Linux](install.md#linux)) and gives the mod a counter for each line. Nothing runs between two changes. When the `perl` process stops, it stops that process group. The clipboard part starts only while the mod is on and after the mod drew its first picture in this session; then the mod starts the process again with the clipboard part (and again without it after `/iui off`). When the counter changes, the mod reads the clipboard one time (`pbpaste` on macOS; `wl-paste`, `xclip`, `xsel` or GTK on Linux). When the clipboard has picture cells that fit a page drawn in this session, the mod shows one toast that names `/iui grab`. It does not change the clipboard. The first counter after a start is not a change, so an old clipboard gets no toast. If the watcher stops, the mod starts it again after 1 s (3 times at most). At `/clear` or a resume, the watcher continues without the clipboard part. At other session ends (for example `/exit`), the mod stops it and does not start a new one.

   `/iui grab` reads the last mouse selection of Claude Code (`$.ui.selection`). With no selection (the main screen), it reads the picture cells on the clipboard. Then it writes their text with `$.ui.copy`. A `ui.copy` hook also changes a copy with picture cells (for example, from `/copy` or `$.ui.copy`) to the text. The mod writes the clipboard only for picture select, `/iui grab` and the `ui.copy` hook.

   A picture cell holds its row and its column (kitty placeholder U+10EEEE plus two combining marks). The mod finds the drawn page that has these rows, at the size that it is drawn. Then it finds the position of each word on that page: it runs the probe (`typst query` on the same template, with the same inputs as the PNG compile, plus `probe=1` and `page=<n>`) only for the pages that a copy reads, and (for picture select) for the pages on the screen. The mod keeps the positions of the last 64 pages in memory. It writes nothing to disk for this, and the PNGs do not change. The mod takes the words in the selected cells.

## Picture select

The selection of Claude Code copies picture cells as kitty placeholder characters, not as text (from Claude Code 2.1.305, it skips picture cells). Thus the mod selects pictures itself (`hooks/lib/select.ts`):

1. Each page is in a `Box` of its size. The last child is a `Client` (`hooks/sel.tsx`) in a `Box` with a negative top margin (the page's rows), so it is over the page. The `Client` draws only an empty `Box` (anything that it draws hides the picture cells). It takes the pointer and posts the selection whole: the anchor, the head, the phase (`down`, `move`, `up` or `clear`; `hover` and `leave` with no button down, refer to item 7 below) and an order. Posts of one frame merge, so a bare event could be lost.
2. The `ui.message` hook keeps the newest selection. The selected rows are in stream order, in the rows of the whole drawing, so a drag can go on into the next page.
3. The highlight does not change the layout. Each page stays one keyed `Image`, and the mod swaps its picture with `$.ui.blit` (`hooks/lib/blit.ts`). This is one small kitty command with the same image id (`a=T`, `t=f`, the file name), so the terminal replaces the picture in place. The frame is the page with the selected cells changed: in a selected cell, each pixel of the page (straight alpha) over the opaque selection colour; in the other cells, the page as it is. A clear swaps the page's own PNG back. Cell `i` is the pixels from `round(i × pixels / cells)` to `round((i + 1) × pixels / cells)`, so the cells cover the page with no gap at any ratio.
4. The hooks runtime has no zlib, so `hooks/lib/png.ts` decodes the page in JavaScript (inflate and unfilter). For each row of cells, the mod makes a deflate piece one time (fixed Huffman codes, matches of one pixel to the left or one pixel up, ended on a byte). A row that is selected whole has a tinted piece, also made one time (in the background, or by a frame: 6 ms of them at most per frame; a row that is not made yet shows plain in that frame, and the next frame continues). A frame makes new pieces only for the first and last selected rows (partly selected), and joins the pieces into one PNG (up to approximately 3 MB for a tall page). The first highlight frame of a ready page takes approximately 2–3 ms to make. The hooks can write only text, so `perl` writes the frame (base64 on its stdin) to `<cache>/select-<id>/f-<n>.png`. The terminal reads the file after the blit. The mod deletes a frame file when 4 newer frames are written and it is 2 s old. The 2-day cleanup of the cache folder deletes the rest.
5. A new frame starts at most once in 16 ms, and only after the last one is blitted. The posts between fold into one frame of the newest selection. If Claude Code refuses a blit, the mod writes the reason one time to the debug log and shows no highlight on that page until the next `down`. The copy still works.
6. At `up`, the mod reads the words under the selected cells the same way as for a copy of these cells (`textOfRun` on the words of the probe), and copies them with `$.ui.copy`. A toast shows "copied N chars of text".
7. Links, file paths, commands and copy buttons (the click targets, `hooks/lib/targets.ts`): the probe also tags the words of a Markdown link (its URL), and the words of inline code (its text). For each code block, it also gives the box of the copy button in the block's header, with the full code and the language (a tag that is not a word, so the copy of a selection does not change). When the words of a page are known, the mod finds its targets (web links, bare URLs, file paths that exist, inline code, which is a command when it is not a file that exists, and the copy button of each code block; the text of a code block is not a target) and the cells of each, one time for each page and size. The cells of a copy button are the cells whose centres are in its box (at least the cell of its centre). An older probe gives no copy buttons, and then a code block has no target. With no button down, the `Client` posts `hover` when the pointer goes to a new cell and `leave` when it goes out. The mod then shows the target under the pointer with the same blits as a selection (step 3), and the page's own PNG when the pointer is off the targets. There is no hover highlight while a selection shows, and a `down` removes it. A `clear` (a click) on a target copies it with `$.ui.copy` (a web link's URL, a file's full path, the text of inline code, the full code of a code block). A later post of one frame replaces an earlier one, so a `hover` or a `leave` also carries the last `up` or `clear` of its `Client`, and the mod reads that one first (by its order, one time).

The `Client` is in the flow, not in an absolute `Box`. Claude Code (2.1.306) moves an absolute `Box` whose top is above the screen down to row 0, with its children. Then the pointer `y` of a `Client` in such a `Box` counts from row 0 of the screen, not from the top of the page, so the selection was too high by the rows that were scrolled away. Also, the `Client` took the pointer under the page. A `Box` in the flow has its true position, also when its top is above the screen.

The mod draws the `Client` only from Claude Code 2.1.298 (`$.session.version()`), which has the `Client`, `ui.message`, `$.ui.blit` and `$.ui.copy`. It draws it only in fullscreen mode, and not over ssh (pages sent as bytes). A `Client` that fails (`ui.fault`) turns picture select off until a reload, and the rows are drawn again with no `Client`. The `Client` sets no key listener: with one, a click would give it the keys of the prompt until Escape, and Escape never reaches it.

A picture selection goes when you type in the prompt (`prompt.edit`, and `prompt.change` for a recalled entry, an undo or a clear) or make a selection of Claude Code: while a picture selection shows, the mod reads `$.ui.selection()` every 250 ms with `$.clock.every` (one timer, stopped with the selection), and a new answer there removes it. No event tells a mod about a plain click outside its region. `/iui details` shows the state on the line `Picture select:`.

### The page cache

The mod gets each page ready for the highlight before the first `down` on it (`hooks/lib/pagecache.ts`). When a page is drawn or comes on the screen (picture select on, fullscreen mode), the mod reads its PNG, decodes it, and makes the deflate piece of each row of cells, in the background. The hooks have no thread and no timer of their own. Thus the mod does this work in short slices: 4 ms at most each (8 ms when a `down` waits for the page), with `$.clock.after(0)` between two slices. Thus scrolling and drawing continue.

- The mod gets one page ready at a time. A page that you push the button on goes first. Then the pages on the screen go, the newest answer first.
- A page that goes off the screen leaves the queue, and its work stops (a `down` on it before its next slice continues that work).
- A drawing that is drawn again with new page files (a stream, a resize, a theme or size change) drops its old pages from the queue.
- When a `down` comes on a different page, the work on the page in progress pauses (if that page is ready, is on the screen, or a `down` asked for it). It continues later.
- When a page is ready, the mod continues with the tinted piece of each row (for a row that is selected whole).
- The mod keeps the decoded pages in memory, 128 MB (a page of 3392 × 4932 pixels uses approximately 74 MB). When it needs space, only pages off the screen go, the oldest first; a page on the screen and the page of the selection stay. A page that does not fit with the pages on the screen waits for a `down` on it (which goes over the budget for a short time). `/iui off` and `/iui select off` let all of it go. It writes nothing of this to disk.
- The mod also finds the words of each page on the screen: it runs the probe of that page (`typst query`, one page at a time). Thus the copy at `up` does not wait.

On Apple Silicon (bun), a page of 3392 × 4284 pixels is ready after approximately 0.24 s of work (about 60 slices of 4 ms, over a longer time). A page of 3392 × 756 pixels is ready after approximately 0.045 s. If a page is not ready at the `down`, the first highlight waits for it: the mod completes that page first, in slices of 8 ms. If the words of a page are not ready at `up`, the copy waits for the probe (approximately 0.05 s for plain text, 0.15–0.5 s for other text, 2–3 s for a page with a large Typst drawing).

## The lean font set

At each start, Typst reads all the fonts of the computer. On macOS, this is approximately 70 ms of each compile. Plain text does not need most of these fonts. Plain text has only ASCII characters, no math outside code, no live Typst block, no image and no HTML entity. In the answers that we measured, approximately 3 of 4 blocks are plain text.

For plain text, Typst loads only these fonts:

- The terminal font.
- The body fonts and the code fonts of the theme, but not the CJK fonts and the emoji fonts.
- The fonts in Typst (for example, the math font).

The mod puts links to these font files in one folder in the cache (`fonts-<hash>`). It gives Typst `--ignore-system-fonts --font-path <folder>`. Then a block of plain text compiles in approximately 0.03–0.07 s, not 0.1–0.15 s. The PNG does not change. For ASCII text, Typst takes each character from the first font of the list that has it, and that font is in the folder. Other text can need a character that no font of the list has. Then Typst looks in all the fonts of the computer, so other text compiles with all the fonts.

The mod makes the folder one time in each session, after the first compile of plain text. `typst fonts --variants` gives the files. The mod does not use the folder in these conditions:

- The first installed font of a list is a CJK font or an emoji font.
- A list has no installed font.
- One style of a font is in two files (then the order in which Typst reads the files can change the font that it uses).
- The list markers or the numbering of the theme are not ASCII.

If a compile with the folder fails, the mod compiles again with all the fonts. The probe of a copy (step 9) uses the same fonts as the PNG compile. If the folder is not there (the cleanup at start deletes folders that are older than 2 days), the mod uses all the fonts and makes the folder again.

## How `auto` is resolved

Claude Code finds the light or dark mode for `auto` by asking the terminal for its background colour (OSC 11). A mod cannot see that answer, so Intelligent UI uses these sources, in this order. The first source that gives an answer is used:

1. **The iTerm2 profile:** the background colour of the profile in use (`ITERM_PROFILE`, else the default profile). Intelligent UI finds iTerm2 by `TERM_PROGRAM`. If `TERM_PROGRAM` is not set, `ITERM_PROFILE`, `ITERM_SESSION_ID` or `LC_TERMINAL=iTerm2` also show iTerm2. If the profile has separate colours for light and dark mode, Intelligent UI uses the set for iTerm2's theme (Settings > Appearance). If that theme is Automatic, Minimal or Compact, it uses the set for the OS appearance.
2. **The Ghostty config:** the `background` that `ghostty +show-config` gives. With a `theme = light:A,dark:B`, Intelligent UI reads the background from the theme file for the OS appearance. With no theme and no `background`, it uses Ghostty's default (`#282c34`, dark).
   - **cmux** (Ghostty inside, found by its `CMUX_*` variables) reads the same Ghostty config, then its own config, `~/Library/Application Support/com.cmuxterm.app/config.ghostty`. The cmux themes picker (Settings > Themes, `cmux themes`) writes the theme there, and that theme wins over the Ghostty config's. A `light:A,dark:B` theme follows cmux's appearance (see below). If these configs set no `theme`, `background`, `foreground` or `palette`, cmux uses its adaptive default theme. Intelligent UI then uses cmux's appearance: `app.appearance` in `~/.config/cmux/cmux.json`, else the value in cmux's Settings. If that appearance is System, Intelligent UI uses the OS appearance. If `terminal.adaptiveDefaultTheme` is `false` in `cmux.json`, Intelligent UI uses the Ghostty rules above.
3. **The kitty config:** the `background` in `kitty.conf` and in the files that it includes (`include` lines only). The themes kitten writes such an include. If the config folder has `dark-theme.auto.conf`, `light-theme.auto.conf` or `no-preference-theme.auto.conf` (kitty 0.38 and later), Intelligent UI uses the file for the OS appearance, as kitty does (on Linux, the portal's or GNOME's colour scheme). With no `background`, it uses kitty's default (`#000000`, dark). The config folder is `KITTY_CONFIG_DIRECTORY`. If that is not set, it is the first of `$XDG_CONFIG_HOME/kitty`, `~/.config/kitty` and (on macOS) `~/Library/Preferences/kitty` that has a `kitty.conf`.
4. **The Rio config:** `config.toml` in `RIO_CONFIG_HOME`, else in `~/.config/rio` (on Linux, `$XDG_CONFIG_HOME/rio` if that is set). With an `[adaptive-theme]`, Intelligent UI reads the theme file for `force-theme`, else for the OS appearance. Else it reads the file for `theme`, else the `[colors] background`. Theme files are in the `themes` folder. With no background, it uses Rio's default (`#0F0D0E`, dark).
5. **`COLORFGBG`**, as it was when Claude Code started. Ghostty does not set it.
6. **The OS appearance:** macOS Dark or Light. On Linux, the `color-scheme` of the freedesktop portal (through `gdbus`, else `busctl`; "no preference" is light), else GNOME's `color-scheme` (`gsettings`). The mod keeps the tool that works, so each check starts one process.
7. **Dark.**

The terminal comes before the OS: a dark terminal on a light Mac is dark.

In **herdr**, `TERM_PROGRAM` is `herdr`, so it does not name the terminal that herdr runs in. Intelligent UI does these steps:

- **Background:** herdr answers OSC 11 with the background of the terminal in front. In herdr, this is source 0, before the sources above. It also works with `herdr --remote`, where the mod runs on the remote computer. Claude Code reads some answers first. If no answer comes, Intelligent UI keeps the last answer until 3 checks in a row get no answer. Then it uses the sources above.
- **Terminal and font:** herdr runs a server, and one or more clients (`herdr`, `herdr --session <name>`, `herdr session attach <name>`) attach to it from terminals. Intelligent UI finds the herdr server above its own process. Then it lists the herdr clients of this user that have a tty (one `ps`). With more than one herdr server, it keeps only the clients that connect to its own server (`lsof`). It uses the client whose tty was read last (the access time of the tty changes when you type in that terminal). It reads the variables of that client (Linux: `/proc/<pid>/environ`; macOS: `ps eww`) and the terminal app above it (the nearest process with no tty). The terminal app comes first, then `TERM`, `TERM_PROGRAM` and the variables of each terminal. Intelligent UI then uses that terminal's sources above (with that client's `ITERM_PROFILE`, `KITTY_CONFIG_DIRECTORY`, `GHOSTTY_BIN_DIR`, `GHOSTTY_RESOURCES_DIR`, `RIO_CONFIG_HOME` and `COLORFGBG`) and its font for the text size. It checks the client every 3 s. When the terminal changes, it reads the font and the background again and draws the pictures again.
- **iTerm2:** herdr runs a terminal of its own for each pane. It draws a picture of Claude Code (kitty placeholder cells) in the outer terminal as one kitty placement for each row, with a source rectangle: row k of a picture that is H pixels tall and R rows tall shows the source rows from floor(k × H / R), floor(H / R) rows tall. iTerm2 3.6 and 3.7 count the top of a source rectangle from the bottom of the image. When the client is iTerm2 (not with `herdr --remote`), Intelligent UI stores each picture with the band of each row at the rows that iTerm2 reads for that row (`hooks/lib/flip.ts`). Before this, a page is made exactly R × B pixels tall (B is a whole number), so the change is the reverse order of the bands. Pictures under rows are first made by Typst at their size in cells. The render key includes this mode, so a change of client draws new files.
- **Fallback:** if it finds no client, it uses the variables that herdr keeps of the terminal that started the herdr server: `CMUX_*` for cmux, `GHOSTTY_RESOURCES_DIR` or `GHOSTTY_BIN_DIR` for Ghostty, `KITTY_PID` or `KITTY_INSTALLATION_DIR` for kitty, `ITERM_PROFILE` for iTerm2. If it finds none, it uses `COLORFGBG`, then the OS appearance.

Intelligent UI checks every 3 s. After a change, each mode's pictures compile once. `/iui probe` asks the terminal for its background with OSC 11 (5 times) and shows the raw answers. This is a test of whether the answer can reach the mod. The 3 s check uses OSC 11 only in herdr.
